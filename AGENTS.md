# Project architecture decisions

- `AddDatasetModal` owns the shared three-step data-asset workflow and supports fullscreen or app-shell presentation, so regular and agentic entry points cannot drift.
- `SetupSessionProvider` (add-dataset-agentic/setup-sessions) owns in-progress agentic setups in localStorage and their open/close state, so navigating away never loses a plan.
- `DomainProvider` owns the selected domain and saves it to localStorage, applied after hydration so server and client render the same first frame. Domain health scores come from `healthFor`, which is a mock standing in for the metric layer; `statusForScore` is the single place that turns a score into good, warn, or bad.
- A chat's `domain` tag is set when the chat is created and is never rewritten, so a chat that later moves focus does not hop between domains in the sidebar. Pinning only applies to chats (never dashboards) and does not change `updatedAt`.
- The sidebar is three zones: global destinations (a "New chat" split button on top, then Dashboards and Tasks), a scrolling region (Pinned, then Recents grouped by domain), and the footer. Recents has a search icon on its header. Each domain row opens that domain's home, its arrow folds its chats, and its plus starts a chat in it; domains sort by lowest health first. Chats with no domain sit in an "All domains" group below them. Every Recents item sits in one group: job chats and failed-run alerts under the job's domain, project chats (kind `project`, id `project-view-<id>`, turns in `agentflow.project-chats.v1`) and add-asset setups under their domain, rule and dashboard chats always under All domains; there is no flat list above the groups. "Tasks" (formerly Jobs) is only the new name of Scheduled; a task is the job definition and a run is one execution (same route `/scheduled`, same behavior); "Dashboards" is the old Data health page at `/`.
- Dashboards (`/`) opens on a grid of cards, each with a score, a 14-day trend and its three lowest rows; selecting a card opens the existing dashboard chat screen, with a "‹ Dashboards" link back.
- Schedules, runs, rules, and dashboards share one mock layer (`lib/mock-ops.ts`) and one localStorage store (`lib/ops-store.ts`, built on `useLocalStore`). A schedule is the job definition; a run is one execution of it. A rule is the shared library definition; a check is a rule a schedule applies to a table.
- Sub-views of Scheduled and Rules (schedule, run, rule, new rule) are search params on `/scheduled` and `/rules`, not separate routes. `/domain?table=` is the domain home, and opening a table keeps the same chat and swaps the right panel.
- Editing a rule that schedules use always goes through the impact check (everywhere, save as new, or some schedules). Only runs that failed or need attention, and have not been opened, reach Recents.
- Explore and DQ checks are no longer under domains in the sidebar; the domain page's Tables and Checks tabs replace them. The old pages remain reachable from search (Cmd/Ctrl+K).


- Feature-specific rules live in `AGENTS.md` inside `src/components/{domain,data-health-brief,scheduled,rules,projects}`.
- Domain-level and table-level Checks tabs reuse `ChecksView` from `table-brief/evidence-panel`, so their table layout and expand/collapse behavior stay identical.
- The Tables Domains filter uses the chat's controlled domain value and scope-change handler, including its post-message lock; panel presentation state belongs to `DomainScreen` so scope changes retain the open tab.
- Opening any object into a chat (rule, job, table, panel item) sends an auto prompt about it when the thread is empty, so every opened object starts as a conversation.
- `SplitWorkspace` always offers Hide chat when a panel exists and renders the Show chat toggle plus floating prompt when collapsed (unless the panel places its own via `ownShowToggle`), so every chat+panel screen hides the same way.
- Every prompt box in the app is `PromptBox` (chat/prompt-box.tsx) with Domain and Project selectors; screens pass controlled domain/project values or it follows the app-wide domain, so no screen has its own composer.
- Project-store reads and creation updates default a missing `created` list to an empty array, so older saved state remains usable without deleting status, owner, or comment edits.
