# Project architecture decisions

- `AddDatasetModal` owns the shared three-step data-asset workflow and supports fullscreen or app-shell presentation, so regular and agentic entry points cannot drift.
- `SetupSessionProvider` (add-dataset-agentic/setup-sessions) owns in-progress agentic setups in localStorage and their open/close state, so navigating away never loses a plan.
- `DomainProvider` owns the selected domain and saves it to localStorage, applied after hydration so server and client render the same first frame. Domain health scores come from `healthFor`, which is a mock standing in for the metric layer; `statusForScore` is the single place that turns a score into good, warn, or bad.
- A chat's `domain` tag is set when the chat is created and is never rewritten, so a chat that later moves focus does not hop between domains in the sidebar. Pinning only applies to chats (never dashboards) and does not change `updatedAt`.
- The sidebar is three zones: global destinations (Search, Data health, Scheduled, Rules), a scrolling region (Pinned, Domains, Recents), and the footer. Domains sort by lowest health first so the ones that need attention are on top. Chat threads live only under Recents (or Pinned), never expanded under a domain; a thread's domain tag is just a label on its Recents row.
- Schedules, runs, rules, and dashboards share one mock layer (`lib/mock-ops.ts`) and one localStorage store (`lib/ops-store.ts`, built on `useLocalStore`). A schedule is the job definition; a run is one execution of it. A rule is the shared library definition; a check is a rule a schedule applies to a table.
- Sub-views of Scheduled and Rules (schedule, run, rule, new rule) are search params on `/scheduled` and `/rules`, not separate routes. `/domain?table=` is the domain home, and opening a table keeps the same chat and swaps the right panel.
- Editing a rule that schedules use always goes through the impact check (everywhere, save as new, or some schedules). Only runs that failed or need attention, and have not been opened, reach Recents.
- "New dashboard" on Data health is also a chat thread (kind `dashboard`, route `/dashboard/$threadId`, state in `agentflow.dashboard-threads.v1`). The starter message is already sent, the agent asks its four questions, and the right panel appears only once the dashboard is built; it then also appears in the Data health dashboard list.
- Principle: pages are fixed and live; nothing is generated when a page loads. Selecting an item opens a chat about it with the question already sent, and chats are saved. Data health: every dashboard is one screen, today's conversation on the left and the dashboard (`DashboardBody`) on the right, chat always present (hide it to get the floating prompt, centered). The conversation is one per dashboard per day (thread id `dashboard-view-<dashId>__<YYYY-MM-DD>`, kind `dashboard`, route `/dashboard/$threadId`, embedded on Data health by `DashboardThreadScreen`). It opens with that day's brief as the first agent message (`briefTurn`, visual kind `brief`: 3 to 5 selectable lines, "Generated today, 6:00am"); a new day starts a new conversation and a new brief, and earlier days stay in Recents. The thread joins Recents with the first question. Selecting a brief line, card, chart row or stat sends "Let's discuss: <topic>" (`dashboard-topics.ts`: `discussPrompt/topicFrom/answerTopic`; items made selectable with `AskItem`/`AskProvider` in `ask.tsx`) into the same chat and highlights the item on the dashboard. Agent answers can carry a chart: `ChatReply = string | {text, visual}` (`workspace/chat-visuals.tsx`: bars, trend, stats, brief; plain data so saved threads restore them; bar rows with `ask` are selectable to dig in). Dashboard answers to a selection always include one.
- Explore and DQ checks are no longer under domains in the sidebar; the domain page's Tables and Checks tabs replace them. The old pages remain reachable from search (Cmd/Ctrl+K).
- Opening a schedule is a chat thread (kind `schedule`, route `/schedule/$threadId`, thread id `schedule-view-<scheduleId>`, one per schedule, state in `agentflow.schedule-threads.v2`), built like the rule and dashboard threads: 59vw right panel, hide/show chat, floating prompt. A schedule opens page-first: the panel is the page at full width with a floating prompt and nothing is said. The chat appears when a conversation starts (a run or item selected, or typing), and only then does the thread join Recents; opening from Recents or search passes `?chat=true` so the saved conversation shows. A run is described only when opened or asked about. The panel has Insights (runs passed, last/next run, checks-passing trend, top failing table and rule bars, tables and rules, click a rule to open its thread), Plan (`PlanView` in `bare` mode with `scheduleToPlan`/`planToSchedule`, always editable) and Runs (list, then a run's results inside the panel). Opening a run, from anywhere (Runs list, Insights, a Recents alert), sends the question "Tell me more about the … run …" for the person and the agent answers; the run opens in the panel at the same time. Run now and Pause/Resume are icon buttons in the panel header; chat can also run, pause, resume, change timing (`parseSchedule`), and add or remove rules. A failed-run alert in Recents opens that schedule's thread with the run in focus (`?run=`). Old `/scheduled?schedule=` and `?run=` links redirect to the thread. The Scheduled list page (Schedules and Runs tabs) remains the index.
- Creating and editing a rule use one screen (`rules/rule-workspace.tsx`): chat in the center, an always-editable editor in the right panel. "New rule" creates a real chat thread (kind `rule`, route `/rule/$threadId`, shown and highlighted in Recents) with the starter message already sent; there is no right panel until the agent has drafted a rule, and no back button to Rules. Thread state (turns, draft, saved rule) persists in `agentflow.rule-threads.v1`. Chat requests (severity, allowed failures, conditions, rename) update the editor and highlight the changed fields. Rules are generic; tables and columns are chosen when a rule is added to a schedule. Table rows offer Duplicate and Disable (Draft rules offer Activate) as icon buttons with tooltips; the whole row opens the rule.
- Opening an existing rule is also a chat thread (kind `rule`, thread id `rule-view-<ruleId>`, one thread per rule, reused on reopen). It opens page-first: the rule's page at full width with a floating prompt and nothing said; the chat appears (and the thread joins Recents) when the first question is asked or an item is selected, and opening from Recents or search passes `?chat=true`. The page has three tabs: Insights (pass rate, trend, top 5 failing table.column bars, coverage by schedule), Edit (created by/when read-only; name, description, DQ dimension, severity, status, owner, parameters; live test; impact check on save) and History. Insights come from `rules/rule-insights.ts`, a mock standing in for the metric layer. A rule's DQ dimension is its `type`. "Save as a new rule" opens the copy in its own thread. Rules not applied by any schedule show "Not applied anywhere yet" and a sample-data test.
